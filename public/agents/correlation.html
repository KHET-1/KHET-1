Multi-Device Drip Correlation

How to source drip from multiple phones, find shared patterns, and cross-reference with desktop/laptop captures

The Core Problem

You have multiple company phones dripping. The question is: are they dripping to the same destination, caused by the same app/process, on the same schedule? And does the desktop/laptop/Mac Mini traffic correlate?

High-Signal Vectors to Source Phone Drip

These are ranked by signal-to-noise ratio — highest signal first. You don't need full pcap from every phone to start correlating.

Vector 1: DNS Queries (Highest Signal, Easiest to Capture)

Why highest signal: Every connection starts with DNS. Even encrypted (HTTPS/QUIC) traffic reveals its destination via DNS lookup. One DNS log from your router shows ALL devices' destinations simultaneously.

HOW TO CAPTURE (one command, covers ALL phones on your network):

# On your router/Pi-hole/Parrot box acting as DNS:
sudo tcpdump -i any port 53 -w /tmp/dns_all.pcap -c 50000

# Or if you run Pi-hole:
pihole -t    # live tail
cat /var/log/pihole.log   # historical

# Or on Parrot box, become the DNS for all phones:
# 1. Set up dnsmasq to log all queries:
echo "log-queries=extra" >> /etc/dnsmasq.conf
echo "log-facility=/var/log/dns_queries.log" >> /etc/dnsmasq.conf
# 2. Set DHCP to hand out your Parrot box IP as DNS server
# 3. All phone DNS now logged with client IP

WHAT YOU GET:
  timestamp | source_phone_IP | query_domain | response_IP
  
  14:03:22 | 192.168.2.100 (iPhone) | graph.facebook.com → 157.240.1.35
  14:03:22 | 192.168.2.101 (Pixel)  | graph.facebook.com → 157.240.1.35
  ^^^ CORRELATION: both phones hitting same service simultaneously
Key insight: If 3 company phones all resolve telemetry.example.com at regular intervals, you've found the drip without touching any phone. DNS is cleartext by default (unless DoH/DoT is enabled).

Vector 2: Destination IP Clustering

Capture at router level. Group all outbound connections by destination IP. If multiple phones talk to the same IP at similar times → shared drip source (same app, same backend).

# Capture all LAN traffic at router/mirror port:
sudo tcpdump -i eth1 -w /tmp/all_traffic.pcap -c 100000

# Then analyze with tshark:
tshark -r /tmp/all_traffic.pcap -q -z endpoints,ip

# Group by destination, correlated across source phones:
tshark -r /tmp/all_traffic.pcap -T fields \
  -e frame.time -e ip.src -e ip.dst -e tcp.dstport \
  | sort -k3 | uniq -f2 -c | sort -rn | head -30

# This shows: which destination IPs are contacted by MULTIPLE source phones

Vector 3: TLS SNI / Server Name (Encrypted Traffic Attribution)

Even with HTTPS, the first TLS handshake packet (ClientHello) sends the server name in cleartext. This is the SNI field. Capture it at the network level — no need to decrypt.

# Extract SNI from all TLS connections on the network:
tshark -r /tmp/all_traffic.pcap \
  -Y "tls.handshake.extensions_server_name" \
  -T fields -e ip.src -e tls.handshake.extensions_server_name \
  | sort | uniq -c | sort -rn

# Output:
#   47  192.168.2.100  graph.facebook.com
#   45  192.168.2.101  graph.facebook.com
#   23  192.168.2.100  api.whatsapp.net
#   22  192.168.2.101  api.whatsapp.net
#   15  192.168.2.100  push.services.mozilla.com
#    8  192.168.2.102  telemetry.suspicious-app.io    ← ONLY on one phone
Triangulation power: SNI tells you WHAT service, source IP tells you WHICH phone, timing tells you WHEN. Three dimensions of correlation without decrypting anything.

Vector 4: Timing/Interval Analysis (Beaconing Detection)

Look for periodic patterns. Phones with the same app will beacon at similar intervals. Your Mac Mini pcaps showed 7.2s — if company phones show similar intervals to different destinations, it's the same app behavior.

# Extract connection timestamps per destination, per source phone:
tshark -r /tmp/all_traffic.pcap -T fields \
  -e frame.time_epoch -e ip.src -e ip.dst -e tcp.dstport \
  -Y "tcp.flags.syn==1 && tcp.flags.ack==0" > /tmp/syn_times.txt

# Then in Python — find shared intervals:
import pandas as pd
df = pd.read_csv('/tmp/syn_times.txt', sep='\t', 
                 names=['time','src','dst','port'])

for dst in df['dst'].value_counts().head(10).index:
    subset = df[df['dst'] == dst]
    for src in subset['src'].unique():
        times = subset[subset['src'] == src]['time'].sort_values()
        intervals = times.diff().dropna()
        if len(intervals) > 3:
            mean = intervals.mean()
            std = intervals.std()
            if std < mean * 0.4:  # Regular = beacon
                print(f"{src} → {dst}: interval={mean:.1f}s σ={std:.1f}s")

Vector 5: Payload Size Fingerprinting

Even encrypted, packet sizes are visible. If the same app does the same request, it produces similar-sized packets. Cluster by (destination, packet_size_distribution) to identify shared app behavior across phones.

# Size distribution per flow:
tshark -r /tmp/all_traffic.pcap -T fields \
  -e ip.src -e ip.dst -e frame.len \
  | awk '{key=$1" "$2; sizes[key]=sizes[key]" "$3} 
    END {for(k in sizes) print k, sizes[k]}' > /tmp/size_profiles.txt

# Phones with matching size profiles to same destination = same app behavior

Vector 6: Connection Burst Correlation

When a phone wakes from sleep, it bursts connections to multiple services simultaneously (push notifications, sync, heartbeats). If multiple phones burst to the same set of IPs at the same wall-clock time → same MDM, same push notification, or same app waking them.

Cross-Referencing Phone Drip with Desktop/Laptop/Mac Mini

The Correlation Matrix

Build this table. If the same destination appears across multiple device types → shared service (corporate MDM, cloud sync, shared app backend).

Destination (SNI/IP) Phone A Phone B Phone C Laptop Mac Mini Verdict
api2.cursor.sh ——— ✓✓ Cursor IDE (desktop only)
graph.facebook.com ✓✓✓ —— Facebook SDK in mobile apps
firebaseinstallations.googleapis.com ✓✓✓ —— Firebase (push + analytics in most Android apps)

192.168.2.151:7734 ——— ✓— Your monitoring script (laptop → Mac Mini)

What to Look For: Shared Drip Indicators

  1. Same destination across all devices → Corporate service (MDM, email, VPN, cloud storage)
  2. Same destination on all phones but NOT desktop → Mobile-specific SDK or push service
  3. Same timing pattern across devices → Centralized push or polling config
  4. Destination only on ONE phone → App unique to that phone, or compromised device
  5. Unknown/suspicious destination on multiple devices → Potential threat actor with multi-device access

Practical: The Capture-Correlate Pipeline

STEP 1: CAPTURE (all at the same time, 5-10 minutes)
─────────────────────────────────────────────────────
# On Parrot box (if router mirror available):
sudo tcpdump -i eth1 -w /tmp/network_all.pcap -G 600 -W 1

# On each Android phone (PCAPdroid or Termux):
curl -sL https://firestar-defense.vercel.app/agents/phone-capture-android.sh | bash

# On Mac Mini:
sudo tcpdump -i any -w /tmp/macmini.pcap -c 20000

# On Laptop:
sudo tcpdump -i any -w /tmp/laptop.pcap -c 20000


STEP 2: UPLOAD ALL TO LATTICE
─────────────────────────────
for f in /tmp/*.pcap; do
  curl -X POST https://firestar-defense.vercel.app/api/ingest \
    -H "Content-Type: application/octet-stream" \
    -H "X-Device-ID: $(hostname)-$(basename $f)" \
    --data-binary @$f
done


STEP 3: CORRELATE (on Parrot box with all pcaps)
────────────────────────────────────────────────
# Extract all SNI across all captures:
for f in /tmp/*.pcap; do
  echo "=== $f ==="
  tshark -r "$f" -Y "tls.handshake.extensions_server_name" \
    -T fields -e ip.src -e tls.handshake.extensions_server_name
done | sort | uniq -c | sort -rn > /tmp/sni_correlation.txt

# Extract all DNS across all captures:
for f in /tmp/*.pcap; do
  tshark -r "$f" -Y "dns.qr==0" \
    -T fields -e ip.src -e dns.qry.name
done | sort | uniq -c | sort -rn > /tmp/dns_correlation.txt

# Find destinations shared by 2+ source IPs:
awk '{print $3}' /tmp/sni_correlation.txt | sort | uniq -c | sort -rn | \
  awk '$1 > 1 {print "SHARED ("$1" devices):", $2}'


STEP 4: IDENTIFY SHARED DRIP
─────────────────────────────
# The output from Step 3 shows:
#   SHARED (4 devices): outlook.office365.com    ← all phones + laptop
#   SHARED (3 devices): graph.facebook.com       ← all phones
#   SHARED (2 devices): api2.cursor.sh           ← laptop + mac mini
#   UNIQUE (1 device):  sketchy-domain.xyz       ← INVESTIGATE THIS ONE

Cell-Specific Vectors (Carrier/Mobile Network)

What's different about phone traffic vs WiFi traffic

When phones are on cellular (not WiFi), you can't capture at your router. Different approach needed:

ScenarioWhat You Can SeeHow
Phone on YOUR WiFi Everything (same as wired) Router mirror / ARP / DNS
Phone on cellular Only what the phone itself reports PCAPdroid (Android) or VPN tunnel back to your network
Phone on cellular + VPN to your network All traffic routed through your infra WireGuard/OpenVPN on Parrot box, phones connect to it
Best approach for cellular phones: Run a WireGuard server on your Parrot box (or Mac Mini). Configure company phones to always-on VPN through it. ALL phone traffic then flows through your network where you can capture it — regardless of whether they're on WiFi or cellular. 
# Set up WireGuard on Parrot box (one-time):
sudo apt install wireguard
wg genkey | tee /etc/wireguard/server_private | wg pubkey > /etc/wireguard/server_public

# /etc/wireguard/wg0.conf:
[Interface]
Address = 10.66.66.1/24
ListenPort = 51820
PrivateKey = SERVER_PRIVATE_KEY

[Peer]  # Phone 1
PublicKey = PHONE1_PUBLIC_KEY
AllowedIPs = 10.66.66.2/32

[Peer]  # Phone 2
PublicKey = PHONE2_PUBLIC_KEY
AllowedIPs = 10.66.66.3/32

# Start:
sudo wg-quick up wg0

# Now capture all phone traffic on the VPN interface:
sudo tcpdump -i wg0 -w /tmp/all_phones_vpn.pcap

# Each phone gets a unique VPN IP → instant per-device attribution

Carrier-Level Drip (what phones do you can't control)

Every phone on cellular constantly talks to carrier infrastructure. This is NOT your drip — it's baseband-level and you cannot control it:

  • RRC signaling — radio resource control (phone → tower negotiation)
  • IMS/VoLTE — always-on SIP registration for calls
  • Carrier push — T-Mobile/AT&T/Verizon push channels
  • SUPL/GPS assist — location services via carrier

You can't see or capture this from WiFi/network level. It only shows up if you have baseband access (root + specialized tools). Ignore this layer — focus on application-layer drip which you CAN control.

Correlation Cheat Sheet

FINDING SHARED DRIP ACROSS DEVICES:

1. DNS is king. One DNS capture at router level → all devices revealed.
2. SNI is queen. Even encrypted traffic shows its destination in TLS ClientHello.
3. Timing is the tiebreaker. Same interval from multiple devices = same app/config.

MATCHING PHONE ↔ DESKTOP:
- Same SNI/DNS destination + same timing = same service/app on both platforms
- Phone-only destinations = mobile SDKs (Firebase, Facebook SDK, Crashlytics)
- Desktop-only destinations = dev tools (Cursor, npm, Docker registries)
- BOTH = corporate services (O365, MDM, Slack, cloud storage)

IDENTIFYING THE ACTUAL APP (on phone):
- Android: PCAPdroid shows process name per connection
- iOS: rvictl pcap + match timing to known app behavior
- Network-only: SNI domain → Google which app uses that domain

RED FLAGS (potential threat vs normal drip):
- Destination contacted by only ONE device when others share the same config
- High-entropy domain names (DGA-generated: adf83jk2.xyz)
- Connections to residential IPs or VPS ranges (DigitalOcean, Linode, Vultr)
- Intervals that shift or jitter deliberately (C2 trying to avoid detection)
- Traffic volume spikes correlated with user activity (keylogger exfil pattern)
