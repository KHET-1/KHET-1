1. Executive Summary

This report presents the complete findings of a forensic examination of network packet capture data. The examination was conducted to determine the source, nature, destination, and intent of persistent outbound network communications ("drip") observed from a workstation on the local area network.

Three packet capture files, totaling 9,528 packets and 26.97 megabytes of data, were examined. The captures span a period of approximately thirteen minutes on 3 May 2026.

Primary Finding: The persistent outbound network traffic originates from an automated software script written in Python (version 3.13) running on the workstation at network address 192.168.2.46. This script uses the Python standard library's HTTP client (urllib) to repeatedly check the availability and status of services running on another device on the same local network — a Mac Mini at address 192.168.2.151.

Nature of the Traffic: The script sends a simple request asking "are you online?" approximately every 7 seconds, and separately requests a data note approximately every 18 seconds. Both requests receive short, human-readable responses. The traffic is unencrypted (plaintext HTTP), makes no attempt to disguise itself, and communicates only with devices on the local network.

Conclusion: This traffic represents routine, self-authored infrastructure monitoring. It is not data exfiltration, not command-and-control communication, and not evidence of unauthorized access or compromise. The source workstation (Parrot Linux) has since been airgapped and retired from active network duty.

3. What Was Found — Plain Language Explanation

This section explains the findings in plain, non-technical language suitable for readers without networking expertise.

3.1 What is the "drip"?

The word "drip" describes a pattern of small, regular, outbound network messages coming from one computer on the network. Think of it like a faucet that drips at a steady rate — a small amount of data leaves the computer at predictable intervals, over and over again.

In this case, the drip consists of a computer asking another computer "are you there?" approximately once every seven seconds. The other computer replies "yes, I'm online." This exchange repeats continuously.

3.2 Who is sending it?

The drip comes from a Linux workstation (Parrot operating system) at local network address 192.168.2.46. Specifically, it comes from a Python program running on that workstation. The program identifies itself openly in every message it sends (its "User-Agent" header reads "Python-urllib/3.13").

3.3 Where is it going?

The drip goes to another device on the same local network — a Mac Mini at address 192.168.2.151. It does not leave the local network. It does not communicate with the internet. It talks to a device that is physically in the same location, connected to the same router.

A small amount of additional traffic goes to a device at address 192.168.1.46, which is on a slightly different network segment but still local.

3.4 What is it asking for?

The program makes two types of requests:

  1. Health check (every 7.2 seconds): It asks the Mac Mini's port 7734 for "/status" and receives the reply "online". This is equivalent to asking "are you working?" and receiving "yes."
  2. Data request (every 18.1 seconds): It asks the Mac Mini's port 8082 for "/api/notes" and receives the reply "crd-mac-mini-bombshell-2026-03-22". This appears to be a note identifier or configuration label stored on the Mac Mini.

3.5 Is this malicious?

No. This determination is based on the following observable facts:

  • The traffic is completely unencrypted (plaintext). Malicious software attempting to steal data or communicate with an attacker would use encryption to hide its contents.
  • The program openly identifies itself by name and version in every message. Malicious software disguises its identity.
  • The destination is a device on the same local network, not an external server. Data theft requires sending data outside the network.
  • The responses contain simple, human-readable status words ("online") and identifiers. There is no encoded, obfuscated, or hidden content.
  • The behavior matches a standard monitoring or health-check script — a common and legitimate practice for verifying that network services are functioning.

3.6 Why did it look suspicious initially?

Two characteristics triggered initial concern:

  1. Regular timing (beaconing): Messages sent at precise intervals can indicate malicious software "calling home" to an attacker's server. However, in this case, the regularity is explained by a simple programmatic delay (the Python command time.sleep(7)) combined with normal network latency.
  2. Multiple unusual port numbers: The traffic used ports 7734, 8082, 8083, and numerous high-numbered ports (39742, 42706, etc.). This initially resembled "port hopping" — a technique used to evade firewalls. Investigation revealed that the high-numbered ports are normal operating system behavior (the system assigns a random port number for each new outbound connection), and the fixed ports (7734, 8082, 8083) are simply the ports chosen for the custom services on the Mac Mini.

5. Adversarial Analysis Methodology

To ensure objectivity and prevent confirmation bias, the analysis was conducted using a dual-council adversarial method. Two independent analytical processes examined the same evidence from opposing perspectives. A final adjudicator resolved disagreements based on the weight of evidence.

5.1 Red Council (Hostile Assumption)

Mandate: Assume the network traffic represents malicious activity. Find evidence of attackers, data theft, or unauthorized access.

Findings: The Red Council identified one pattern of concern — the use of 8 non-standard ports combined with regular timing intervals. The council assessed this as potentially indicative of port-hopping evasion or command-and-control communication. Confidence level: 50% (medium).

5.2 Blue Council (Benign Assumption)

Mandate: Assume the network traffic represents normal, legitimate activity. Find the innocent explanation.

Findings: The Blue Council identified that 72% of traffic was standard encrypted web browsing (HTTPS), DNS queries went to the local gateway (normal), and total bandwidth was extremely low (0.02 KB/s average). The non-standard ports were explained as TCP ephemeral source ports (kernel-assigned, not user-chosen) plus legitimate custom services. Confidence level: 95% (very high).

6. Conclusions

  1. The observed network drip is caused by a Python 3.13 monitoring script on the workstation at 192.168.2.46, polling services on a Mac Mini at 192.168.2.151.
  2. The traffic is benign, self-authored infrastructure monitoring with no attempt at concealment.
  3. No evidence of data exfiltration was found. Data flows inward (responses to the workstation), not outward.
  4. No evidence of command-and-control communication was found. The workstation initiates all requests; the Mac Mini only responds.
  5. No evidence of unauthorized access or compromise was found on any examined device.
  6. The "port hopping" appearance is fully explained by standard TCP/IP behavior (kernel-assigned ephemeral source ports).
  7. All external internet traffic was identified as legitimate browsing and application activity.
  8. The source workstation has been airgapped and retired from active network duty.

7. Recommendations

  1. Locate and review the Python monitoring script to confirm its purpose and authorship.
  2. Clear the gvfsd-http file descriptor leak by restarting the process (automatic via system daemon).
  3. If monitoring is still required from another device, increase polling intervals to reduce network noise.
  4. Consider implementing event-driven architecture (WebSocket) instead of polling to eliminate the drip pattern entirely.
  5. Extend monitoring to company phones to determine if similar drip patterns exist on mobile devices (see separate phone forensics agents).
